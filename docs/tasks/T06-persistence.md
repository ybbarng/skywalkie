### 표

[05-messaging-spec.md](../05-messaging-spec.md)의 SQL 그대로 만든다. 두 가지를 데이터베이스가 직접 막는 것이 요점이다.

- `PRIMARY KEY (id)` — 같은 메시지가 두 번 들어가지 않는다
- `UNIQUE (author_id, seq)` — 한 사람의 같은 순번이 두 개일 수 없다

코드에서 실수해도 저장소가 걸러낸다.

### 표를 고칠 때

버전을 기록하는 표를 하나 두고, 올릴 때마다 필요한 것만 실행한다. 앱을 새로 깔지 않아도 예전 대화가 살아남아야 하므로 이게 필요하다.

**표를 고칠 때는 절대 메시지를 지우지 않는다.** 이 원칙을 마이그레이션 파일 맨 위에 주석으로 적어둔다.

### 화면에 꺼내기

`OFFSET`을 쓰지 않는다. 메시지가 쌓이면 뒤로 갈수록 느려진다.

```ts
loadPage(before?: { receivedAt: number; id: string }, limit = 50)
```

마지막으로 본 지점을 받아 그 앞을 찾는다. 만 건이 있어도 늘 같은 속도다.

### 변화 알리기

메시지가 들어오면 화면이 알아야 한다. 저장소가 바뀜을 알리는 통로를 둔다.

## 테스트

메모리에 데이터베이스를 띄워 실제 SQL로 시험한다. 가짜로 대신하지 않는다. **SQL 자체가 맞는지를 확인하는 게 목적이기 때문이다.**

- 같은 id를 두 번 넣으면 실패한다
- 같은 (보낸이, 순번)을 두 번 넣으면 실패한다
- 만 건을 넣고 꺼내는 시간이 첫 쪽이나 마지막 쪽이나 비슷하다
- 표를 올리기 전후로 메시지가 그대로다
- 저장 중에 앱이 죽어도(트랜잭션 중단) 반쯤 들어간 메시지가 없다

## 끝난 걸 어떻게 아는가

- [x] 앱을 껐다 켜도 대화가 남아 있다
- [x] 만 건에서 화면 넘김이 16밀리초 안에 끝난다
- [x] 적용 범위 90% 이상

## 하면서 알게 된 것

### SQL 을 진짜로 시험할 방법을 찾았다

`expo-sqlite` 는 네이티브 코드라 Node 에서 안 돈다. 저장소를 통째로 가짜로
만들면 **정작 확인하고 싶은 SQL 이 시험되지 않는다.**

Node 24 에 `node:sqlite` 가 들어 있는 걸 발견했다. 그래서 `SqlDatabase`
라는 얇은 약속만 두고

- 앱에서는 `expo-sqlite` 를 끼우고
- 테스트에서는 `node:sqlite` 를 끼운다

둘 다 진짜 SQLite 라서 기본 키가 진짜로 중복을 막는지, 색인이 실제로
걸려 있는지, 표를 올려도 메시지가 남는지를 전부 확인할 수 있다.

### 대화를 되살리는 방법을 바꿨다

처음에는 저장된 메시지를 하나씩 `accept` 하며 되살리려 했다. 두 가지가
어긋났다.

- **이미 읽은 메시지까지 안 읽음으로 다시 세어진다**
- 만 건이면 앱을 켜는 데 그만큼 걸린다

그래서 도메인에 `Conversation.restore` 를 두고, 저장소가 요약한 값
(내 최대 순번, 사람별 받은 순번, 읽지 않은 개수)만 넘기게 했다.
만 건에서 되살리는 데 드는 시간을 테스트로 고정했다.

중간에 캡슐화를 뚫고 내부 값을 직접 세우는 코드를 썼다가 되돌렸다.
도메인에 명시적인 복원 경로를 두는 게 맞다.

### 내가 보낸 메시지를 줄 세우는 문제

내가 보낸 메시지는 받은 시각이 없다. `received_at` 으로만 줄 세우면
내 메시지가 전부 맨 앞이나 맨 뒤로 몰린다. `COALESCE(received_at, sent_at)`
으로 바꿔 대화가 뒤죽박죽이 되지 않게 했다.

### 같은 밀리초에 여러 건이 들어올 때

빠르게 주고받으면 실제로 생긴다. 시각만으로 줄 세우면 화면을 넘길 때마다
순서가 달라진다. 식별자까지 넣어 순서를 확정했다.
