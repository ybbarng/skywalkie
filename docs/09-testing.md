# 테스트

> 상태: 확정 · 최종 수정 2026-09-17

## 1. 무엇을 지키려는 것인가

이 앱은 **고칠 기회가 한 번뿐이다.** 비행기 안에서 버그를 발견하면 그걸로 끝이다. 앱 스토어 업데이트도, 서버 수정도 없다.

그래서 테스트의 목적은 "커버리지 숫자"가 아니라 **비행기에서 벌어질 일을 땅 위에서 미리 겪어보는 것**이다. 그 기준으로 어디에 힘을 줄지 정한다.

## 2. 어디에 힘을 주는가

```
        적게 ┌──────────────┐
             │  손으로 확인  │  실제 두 폰으로. 자동화 못 하는 것
             ├──────────────┤
             │  화면 테스트  │  주요 흐름만
             ├──────────────┤
             │  이어붙임     │  ★ 두 기기가 대화하는 전 과정
             ├──────────────┤
        많이 │  단위 테스트  │  ★ 도메인과 응용 계층 전부
             └──────────────┘
```

별표 친 두 층이 중심이다. 이유가 있다.

- **도메인·응용 계층**은 진짜 Wi-Fi 없이 전부 시험할 수 있다. 앱의 규칙이 여기 모여 있으므로 여기를 지키면 대부분의 논리 오류를 잡는다.
- **이어붙임 테스트**는 두 기기를 흉내내어 주고받는 전 과정을 컴퓨터에서 돌린다. 이 앱의 가장 큰 위험이 "두 기기 사이"에 있으므로 여기가 가장 값지다.

화면 테스트는 주요 흐름만 본다. 버튼 색 같은 것까지 시험하면 화면을 고칠 때마다 테스트가 깨져서 오히려 손해다.

## 3. 반드시 시험하는 것

### 도메인

| 대상 | 무엇을 확인하나 |
|---|---|
| `Message` | 잘못된 내용으로는 만들어지지 않는다 |
| `DeliveryState` | 읽음에서 전달됨으로 되돌아가지 않는다. 모든 전이 조합을 확인 |
| `Conversation` | 같은 id를 두 번 받지 않는다. 순번의 빈틈을 정확히 찾아낸다 |
| `LinkQuality` | 점수 계산이 맞다 |
| `ConnectionState` | 상태 전이가 규칙을 따른다 |
| `Character` | 고른 값이 유효하다 |

### 응용

| 대상 | 무엇을 확인하나 |
|---|---|
| `SendMessage` | **보내기 전에 저장한다.** 전송이 실패해도 메시지가 남는다 |
| `ReceiveMessage` | 같은 메시지가 두 번 와도 하나만 남는다 |
| `FlushPendingMessages` | 쌓인 순서대로 나간다. 5번 실패하면 멈춘다 |
| `SelectBestLink` | 점수가 높은 길을 고른다. 갈아탈 때 메시지를 흘리지 않는다 |
| `ExportConversation` | 만 건을 내보내도 메모리가 터지지 않는다 |
| `ImportConversation` | 같은 파일을 두 번 불러도 두 배가 되지 않는다. 검증값이 어긋나면 멈춘다 |
| `PushToTalk` | 누르고 떼는 순서가 꼬여도 마이크가 켜진 채 남지 않는다 |

### 통신 규약

**이게 가장 중요한 묶음이다.**

| 무엇 | 어떻게 |
|---|---|
| 바이트 자르기 | 한 번에 온 것, 잘려서 온 것, 붙어서 온 것을 전부 올바로 나눈다 |
| 이상한 길이 값 | 1 MB를 넘는다고 주장하면 연결을 끊는다 |
| 모르는 봉투 | 새 종류가 와도 연결이 유지된다 |
| 망가진 내용 | 형식 검사에서 걸러지고 앱이 죽지 않는다 |
| 순번 | 빠짐·겹침·뒤바뀜을 각각 올바로 다룬다 |
| 인사 | 버전이 다를 때 낮은 쪽에 맞춘다 |
| 블루투스 조각내기 | 조각내고 다시 붙이면 원래 값과 같다 |
| 조각 유실 | 하나가 안 오면 그 묶음을 버린다 |

**아무 바이트나 던져도 앱이 죽지 않는지**를 별도로 확인한다. 무작위 값을 수천 번 넣어보는 방식(퍼즈)을 쓴다. 상대가 다른 버전이거나 누가 장난칠 수 있기 때문이다.

### 두 기기가 대화하는 전 과정

가짜 연결 두 개를 이어 붙여 한쪽에서 보낸 것이 다른 쪽에 도착하는지 확인한다. 진짜 Wi-Fi가 필요 없다.

```
시험하는 장면:
  · 인사부터 메시지 한 통이 도착하기까지
  · 도중에 끊겼다 붙었을 때 놓친 것이 채워지는가
  · Wi-Fi에서 블루투스로 갈아탈 때 메시지가 흘러내리지 않는가
  · 양쪽이 동시에 보낼 때 순서가 유지되는가
  · 한쪽만 재시작했을 때 다시 붙는가
  · 100통을 연달아 보낼 때 순서가 유지되는가
```

## 4. 시간과 무작위를 다루기

테스트가 어떤 날 갑자기 실패하는 일을 막는다.

- **시간**: `Date.now()`를 직접 부르지 않는다. `Clock`을 주입받아 쓴다. 테스트에서는 시간을 손으로 돌린다. 다시 보내는 간격(1초, 2초, 4초…)을 시험할 때 진짜로 기다리지 않아도 된다.
- **식별자**: ULID를 만드는 것도 주입받는다. 테스트에서는 정해진 값이 나오게 한다.
- **무작위**: 씨앗을 고정한다. 실패하면 같은 순서로 다시 재현할 수 있다.

## 5. 가짜 부품

응용 계층이 요구하는 약속마다 가짜 구현을 하나씩 둔다.

```
test/fakes/
  FakeMessageTransport.ts       보낸 것을 기록. 실패를 시킬 수 있다
  FakeConversationRepository.ts  메모리에만 저장
  FakeClock.ts                   시간을 손으로 돌린다
  FakePeerDiscovery.ts           찾았다고 알려준다
  FakeCallSession.ts             통화를 흉내
  FakeAudioController.ts         소리 설정 변화를 기록
  LinkedTransportPair.ts         ★ 두 기기를 이어붙인다
```

`LinkedTransportPair`가 핵심 도구다. 두 개의 가짜 연결을 서로 묶어서 한쪽에 넣은 것이 다른 쪽으로 나오게 한다. 지연, 유실, 순서 뒤바뀜을 일부러 만들 수도 있다.

```ts
const [a, b] = linkedTransportPair({
  latencyMs: 50,
  dropRate: 0.1,      // 10%를 일부러 잃어버린다
  reorder: true,
})
```

## 6. 자동으로 못 하는 것

실제 기기가 있어야만 확인되는 것들이다. 이건 손으로 한다.

```
연결
  □ 안드로이드 핫스팟을 켜고 아이폰이 붙는다
  □ 두 폰 다 비행기 모드에서도 된다        ← 가장 중요
  □ 핫스팟을 껐다 켜면 자동으로 다시 붙는다
  □ 앱을 껐다 켜도 다시 붙는다

소리 (이어폰을 실제로 껴야 확인된다)
  □ 음악을 틀고 통화할 때 음악이 안 꺼진다
  □ 상대가 말하면 음악이 작아지고 끝나면 돌아온다
  □ 방식 2(폰 마이크)에서 이어폰 음질이 안 떨어진다
  □ 에어팟을 뺐다 끼면 소리가 엉키지 않는다
  □ 버즈 프로와 무선 헤드폰에서도 된다
  □ 화면을 끄고도 대화가 이어진다

영상
  □ 얼굴이 보이고 소리가 맞는다
  □ 앞뒤 카메라가 바뀐다
  □ 앱을 뒤로 보내면 영상이 멈추고 소리는 이어진다

보관
  □ 내보낸 파일을 다시 불러오면 대화가 그대로다
  □ 아이폰 앱을 덮어쓰기로 다시 깔아도 대화가 남는다
  □ HTML 파일이 브라우저에서 제대로 열린다

버티기
  □ 한 시간 동안 연결을 유지한다
  □ 대기 상태에서 배터리가 시간당 5% 이내로 준다
  □ 메시지 천 통을 넣어도 화면이 버벅이지 않는다
```

이 점검표는 [08-build-release.md](./08-build-release.md)의 여행 전 점검표와 이어진다.

## 7. 어느 정도까지 시험하나

숫자를 목표로 삼지 않되, 층별로 기대치를 둔다.

| 층 | 기대 | 왜 |
|---|---|---|
| domain | 95% 이상 | 순수한 코드라 안 할 이유가 없다 |
| application | 90% 이상 | 앱의 절차가 여기 있다 |
| (분기만) | 75~90% | 아래 설명 참고 |
| infrastructure — 규약 부분 | 90% 이상 | 바이트를 다루는 곳이라 실수가 잦다 |
| infrastructure — 기기에 닿는 부분 | 시험하지 않음 | 진짜 기기가 필요하다. 손으로 확인 |
| presentation | 주요 흐름만 | 화면은 자주 바뀐다 |

**분기(branch) 기준만 낮게 잡은 이유**: 측정 도구(v8)가 기본값과 옵셔널 파라미터까지 분기로 센다. 실제로는 다 시험했는데도 숫자가 낮게 나온다. 여기에 맞추려고 의미 없는 테스트를 늘리면 오히려 손해다. 숫자를 채우는 대신 "무엇이 잘못될 수 있는가"를 보고 테스트를 고른다.

## 8. 돌리는 법

```bash
pnpm test              # 한 번 돌린다
pnpm test:watch        # 고칠 때마다 다시 돌린다
pnpm test:coverage     # 어디가 안 시험됐는지 본다
pnpm test:protocol     # 통신 규약만
pnpm typecheck         # 타입
pnpm lint              # 형식과 흔한 실수
pnpm check:deps        # 층이 규칙을 어기지 않는지
pnpm verify            # 위를 전부
```

커밋할 때 `lint`와 `typecheck`가, 올릴 때 `verify` 전체가 자동으로 돈다. lefthook이 한다.

## 9. 테스트를 쓰는 규칙

- 이름은 **무엇을 보장하는지** 한국어로 적는다. `"읽음 상태에서 전달됨으로 되돌아가지 않는다"`처럼.
- 한 테스트는 하나만 확인한다.
- 준비·실행·확인 세 덩어리로 나누고 빈 줄로 구분한다.
- 가짜 부품을 만들 때 실제 구현과 같은 인터페이스를 쓴다. 그래야 실제가 바뀌면 가짜도 같이 깨진다.
- 내부 구현을 시험하지 않는다. 밖에서 보이는 행동만 시험한다. 그래야 구조를 고쳐도 테스트가 살아남는다.
