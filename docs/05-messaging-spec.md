# 메시지와 보관

> 상태: 확정 · 최종 수정 2026-09-17

## 1. 메시지란 무엇인가

한 사람이 특정 시각에 상대에게 보낸 한 덩어리의 내용이다. 한 번 보내면 내용은 바뀌지 않는다. 바뀌는 건 **어디까지 갔는지**뿐이다.

```
Message
├─ id           ULID. 전 세계에서 겹치지 않는 값
├─ author       누가 보냈나
├─ content      무엇을 보냈나
├─ sentAt       언제 보냈나 (보낸 기기 시각)
├─ receivedAt   언제 받았나 (받은 기기 시각, 내가 보낸 것이면 없음)
├─ seq          보낸 사람 기준 순번
└─ delivery     어디까지 갔나
```

### 왜 ULID인가

시각이 앞에 들어간 식별자라 **정렬하면 시간순이 된다.** 두 기기가 각자 만들어도 겹치지 않는다. 그래서 내보낸 파일을 합칠 때 같은 메시지인지 판단하는 기준으로 쓸 수 있고, 동시에 순서도 알려준다.

### 왜 시각이 두 개인가

두 폰의 시계가 다를 수 있다. 특히 시차를 넘는 비행에서는 한쪽이 먼저 시간대를 바꿀 수 있다.

- 화면에 보여줄 때는 **받은 시각**을 기준으로 줄 세운다. 내 기기에서 본 순서가 흐트러지지 않는다.
- 보낸 시각은 같이 저장해두고, 두 시각이 크게 어긋나면 화면에 작게 표시한다.

## 2. 보낼 수 있는 것

```
MessageContent
├─ Text        글자. 최대 4000자
├─ Doodle      낙서. 선의 좌표 묶음
├─ Nudge       콕 찌르기. 내용 없음
├─ Photo       사진 (2단계)
├─ Sticker     캐릭터 이모티콘 (2단계)
└─ System      앱이 끼워 넣는 알림 ("연결이 끊겼어요" 등)
```

낙서를 그림 파일이 아니라 **선의 좌표로** 저장하는 이유가 있다. 크기가 훨씬 작아서 블루투스로도 나를 수 있고, 화면 크기가 달라도 선명하게 다시 그릴 수 있다.

```ts
Doodle = {
  strokes: Array<{
    points: Array<[x: number, y: number]>   // 0~1 사이 비율 좌표
    color: string                            // 토큰 이름. 실제 색이 아님
    width: number
  }>
}
```

색을 `#FF0000` 대신 토큰 이름으로 저장하는 이유는, 어두운 화면과 밝은 화면에서 각각 알맞은 색으로 나오게 하기 위해서다.

### 사진 (2단계)

사진은 다른 내용과 달리 **봉투 안에 담기지 않는다.** 너무 크기 때문이다. 메시지에는 사진에 대한 설명만 넣고, 실제 그림은 따로 나른다.

```ts
Photo = {
  assetId: string      // 이 사진의 고유 번호
  width: number
  height: number
  byteSize: number
  blurHash: string     // 20자 남짓의 흐릿한 미리보기
  localUri?: string    // 내 기기에서의 위치. 상대에게 보내지 않는다
}
```

`blurHash`가 중요하다. 스무 자 남짓한 짧은 글자에 사진의 색과 형태가 담긴다. **사진이 다 오기 전에 흐릿한 모습을 먼저 보여줄 수 있다.** 받는 동안 빈 네모를 보고 있지 않아도 된다.

사진을 나르는 절차:

```
보내는 쪽                              받는 쪽
   │                                      │
   │─ message { photo, assetId, blurHash }▶│  먼저 메시지가 간다
   │                                      │  → 흐릿한 미리보기가 즉시 뜬다
   │                                      │
   │─ asset_offer { assetId, 크기, 조각수 }▶│
   │◀─ asset_request { assetId, 필요한 조각 }│
   │                                      │
   │─ asset_chunk { assetId, 번호, 내용 } ─▶│  (여러 번)
   │─ asset_chunk ... ────────────────────▶│
   │                                      │
   │◀─ asset_complete { assetId, 검증값 } ──│
```

- 한 조각은 48 KB다. 받는 쪽이 어디까지 받았는지 알고 있어서, 끊겼다 붙으면 **못 받은 조각만** 다시 요청한다.
- 조각을 전부 받으면 검증값을 대조한다. 어긋나면 그 사진만 다시 받는다.
- 사진은 앱 폴더의 `photos/` 아래에 `assetId`를 이름으로 저장한다.
- 보내는 쪽도 줄인 사진을 같은 곳에 저장한다. 내가 보낸 사진도 나중에 다시 봐야 하기 때문이다.
- 블루투스로는 보내지 않는다. 대기 줄에 두고 Wi-Fi가 열리면 내보낸다.

### 이모티콘 (2단계)

```ts
Sticker = {
  character: CharacterId    // 어느 캐릭터인지
  pose: StickerPose         // wave | sleep | heart | laugh | cry | thumbsUp | eat | bored
}
```

그림을 나르지 않는다. **어떤 캐릭터가 어떤 자세인지**만 보내면 받는 쪽이 코드로 그린다. 그래서 몇십 바이트면 충분하고 블루투스로도 즉시 간다.

### 반응 (2단계)

메시지에 이모지를 붙이는 것이다. 새 메시지가 아니라 **기존 메시지에 딸린 표시**다.

```sql
CREATE TABLE reactions (
  message_id  TEXT NOT NULL,
  peer_id     TEXT NOT NULL,
  emoji       TEXT NOT NULL,
  created_at  INTEGER NOT NULL,
  PRIMARY KEY (message_id, peer_id)
);
```

한 사람이 한 메시지에 붙이는 반응은 하나다. 새로 붙이면 이전 것이 바뀐다. 그래서 늦게 도착한 반응이 순서가 뒤바뀌어도 시각을 비교해 최신 것만 남긴다.

## 3. 어디까지 갔나

```
  작성됨 ──▶ 보내는 중 ──▶ 전달됨 ──▶ 읽음
    │            │
    │            ▼
    └────────▶ 대기 중 ──▶ (연결되면 다시 보내는 중)
                 │
                 ▼
               실패
```

규칙:

- **뒤로 못 간다.** 읽음이 된 메시지가 전달됨으로 돌아가지 않는다. 늦게 도착한 옛 신호가 화면을 흔드는 걸 막는다.
- **실패에서는 다시 시작할 수 있다.** 사용자가 다시 보내기를 누르면 대기 중으로 돌아간다.
- 이 규칙은 `DeliveryState`가 직접 강제한다. 잘못된 전이를 요청하면 값이 바뀌지 않고 실패를 돌려준다.

### 대기 중인 메시지 내보내기

연결이 끊긴 동안 보낸 메시지는 **순번 순서 그대로** 쌓인다. 다시 붙으면 쌓인 순서대로 내보낸다. 순서가 뒤바뀌면 대화가 이상해지기 때문이다.

한 메시지는 최대 5번까지 다시 보낸다. 그래도 안 되면 실패로 두고 화면에 다시 보내기 버튼을 띄운다.

## 4. 대화

메시지를 모아둔 것이 대화(Conversation)다. 두 사람이 쓰므로 대화는 하나뿐이다.

대화가 책임지는 일:

- 메시지를 받아들일지 판단한다. 이미 있는 id면 거절한다.
- 순번의 빈틈을 찾아낸다. "3, 4, 6이 왔으니 5가 없다"를 알려준다.
- 읽지 않은 개수를 센다.

메시지가 수만 개가 되어도 문제없도록, 대화 객체가 **전부를 메모리에 안고 있지 않는다.** 화면에 보이는 구간만 데이터베이스에서 꺼내 쓴다.

## 5. 저장

### 표 구조

```sql
CREATE TABLE messages (
  id            TEXT PRIMARY KEY,           -- ULID
  author_id     TEXT NOT NULL,
  content_kind  TEXT NOT NULL,              -- text | doodle | nudge | system
  content_body  TEXT NOT NULL,              -- JSON
  sent_at       INTEGER NOT NULL,           -- 밀리초
  received_at   INTEGER,
  seq           INTEGER NOT NULL,
  delivery      TEXT NOT NULL,
  link_kind     TEXT,                       -- 어느 길로 왔나 (wifi | ble | web)
  UNIQUE (author_id, seq)
);

CREATE INDEX idx_messages_received_at ON messages (received_at DESC, id DESC);
CREATE INDEX idx_messages_delivery ON messages (delivery) WHERE delivery IN ('pending','failed');
```

두 가지를 데이터베이스가 직접 막는다.

- `PRIMARY KEY (id)` — 같은 메시지가 두 번 들어가지 않는다.
- `UNIQUE (author_id, seq)` — 한 사람의 같은 순번이 두 개일 수 없다.

코드에서 실수해도 저장소가 걸러낸다.

### 화면에 꺼내는 법

최신부터 50개씩 꺼낸다. 위로 올리면 더 꺼낸다.

`OFFSET`을 쓰지 않는다. 메시지가 쌓이면 뒤로 갈수록 느려지기 때문이다. 대신 **마지막으로 본 지점을 기준으로** 그 앞을 찾는다.

```sql
SELECT * FROM messages
WHERE (received_at, id) < (?, ?)
ORDER BY received_at DESC, id DESC
LIMIT 50;
```

## 6. 보관과 내보내기

> 제품 명세 F2-1에 대응한다. 아이폰 앱이 7일마다 만료되므로 이건 필수 기능이다.

### 6.1 세 가지 형식

| 형식 | 확장자 | 무엇에 쓰나 | 되돌릴 수 있나 |
|---|---|---|---|
| 보관 파일 | `.skywalkie.json` | 다른 기기로 옮기거나 재설치 후 되돌리기 | **가능** |
| 읽는 문서 | `.html` | 앱 없이 그냥 열어보기. 낙서까지 보인다 | 불가 |
| 글자만 | `.txt` | 어디서든 열리는 가장 단순한 형태 | 불가 |

한 번 내보낼 때 **세 개를 다 만든다.** 사용자가 고르게 하면 잘못 고를 수 있다.

### 6.2 보관 파일의 생김새

```jsonc
{
  "format": "skywalkie-archive",
  "version": 1,
  "exportedAt": 1758000000000,
  "people": [                       // 두 사람 다 담는다
    { "peerId": "...", "displayName": "...", "character": "..." },
    { "peerId": "...", "displayName": "...", "character": "..." }
  ],
  "messages": [ /* ... */ ],
  "integrity": {                    // 맨 끝에 온다
    "messageCount": 1523,
    "checksum": "sha256:...",       // 메시지 id를 정렬해 이은 값의 해시
    "firstMessageId": "01J...",
    "lastMessageId": "01J...",
    "sourceCount": 1523             // 꺼내기 시작할 때 저장소가 답한 수
  }
}
```

**두 사람을 다 담는다.** 내 것만 담으면 상대 이름과 캐릭터가 사라져서, 나중에
파일을 열었을 때 누가 한 말인지 알 수 없다.

**`integrity`가 맨 끝에 온다.** 흘려가며 쓰는 것과 검증값을 앞에 두는 것은 같이
할 수 없다. 다 읽어봐야 나오는 값이기 때문이다. JSON 은 자리 순서를 따지지 않는다.

### 검증값이 두 겹인 이유

`checksum`은 **파일이 옮겨지다 망가진 것**을 잡는다. 되돌릴 때 다시 계산해 대조한다.

`sourceCount`는 **꺼내다 만 것**을 잡는다. 이건 `checksum`으로는 못 잡는다.
저장소가 중간에 한 건을 해석하지 못하면 거기서 멈추는데, 그러면 나머지가 없는 채로
**스스로는 앞뒤가 맞는 파일**이 나오기 때문이다. 건수도 맞고 검증값도 그 상태로
계산된다. 그래서 **파일 바깥에서 온 수**를 따로 적어둬야 한다.

예전 파일에는 `sourceCount`가 없다. 없으면 이 확인을 건너뛴다. 새 검사를 들이면서
예전 파일을 못 열게 만들면 "대화가 앱보다 오래 산다"는 목적과 어긋난다.

메시지가 만 개를 넘어도 되도록 **한 번에 다 읽지 않고 흘려가며** 쓰고 읽는다.

### 6.3 되돌리기

```
파일 고르기
   │
   ▼
형식과 버전 확인 ──── 안 맞으면 ──▶ "이 파일은 이 앱이 만든 게 아니에요"
   │
   ▼
검증값 대조 ──────── 어긋나면 ──▶ "파일이 손상됐어요. 그래도 불러올까요?"
   │                                        │ (사용자가 원하면)
   ▼                                        ▼
한 건씩 넣기 (id가 이미 있으면 건너뛴다)
   │
   ▼
결과 알리기: "1,523건 중 1,200건을 새로 넣었어요. 323건은 이미 있었어요."
```

**겹쳐도 안전하다.** 같은 파일을 두 번 불러도 메시지가 두 배가 되지 않는다. id가 기준이기 때문이다.

**멀쩡한 파일이면 한 건이라도 이상할 때 하나도 넣지 않는다.** 반쯤 넣고 알려주면
이미 늦다. 먼저 전부 확인하고 통과해야 넣는다.

**"그래도 불러올까요?"로 들어온 경우는 다르다.** 이때는 읽을 수 없는 한 건 때문에
나머지를 버리지 않는다. 되살릴 수 있는 것만 넣고 몇 건을 못 읽었는지 알린다.
거절만 하면 그 파일이 하나뿐일 때 통째로 잃기 때문이다.

> 1,523건 중 1,200건을 넣었어요.
> 6건은 읽을 수 없었어요.

다만 **파일을 뜯지도 못하면 이 길도 없다.** 건질 것이 없어서 억지로 넘어가도
할 수 있는 게 없다.

내 프로필까지 덮어쓸지는 물어본다. 상대 기기의 보관 파일을 잘못 불러와 내 캐릭터가 바뀌는 일을 막는다.

### 6.4 자동 보관

사용자가 잊어도 최소한은 남게 한다.

- 앱이 뒤로 갈 때마다 마지막 자동 보관 시각을 확인한다. 24시간이 지났으면 새로 만든다.
- 앱 내부의 **문서 폴더**에 저장한다. 아이폰에서는 파일 앱을 통해 사용자가 직접 꺼낼 수 있는 위치다.
- 최근 3개만 남기고 오래된 것은 지운다.
- 만드는 데 시간이 걸리므로 화면을 막지 않는다.

### 6.5 만료 전 알림

아이폰에서 앱을 설치한 날짜를 기록해둔다. 7일 중 4일이 지나면 앱을 열 때 한 번 알린다.

> **3일 뒤면 이 앱이 열리지 않아요.**
> 대화를 파일로 꺼내두면 다시 설치한 뒤에도 그대로 볼 수 있어요.
> [지금 꺼내기] [나중에]

이 알림에서 바로 내보내기가 실행된다. 설정 화면까지 찾아 들어가게 하지 않는다.

## 7. 입력 중 표시

- 글자를 치기 시작하면 `typing`을 보낸다. 그 뒤 3초에 한 번씩만 다시 보낸다. 글자마다 보내면 낭비다.
- 받은 쪽은 5초 동안 새 신호가 없으면 표시를 지운다.
- 블루투스로 붙어 있을 때는 이 신호를 아예 보내지 않는다. 좁은 길을 실제 대화에 양보한다.

## 8. 읽음 표시

- 화면에 메시지가 실제로 보이고 앱이 앞에 있을 때만 읽음으로 친다.
- 여러 건이 한꺼번에 읽히므로 **묶어서 한 번에** 보낸다.
- 읽음 신호가 못 갔다고 해서 다시 보내지는 않는다. 중요도가 낮고 다음 신호가 덮어쓰기 때문이다.
