## D1. 두 기기를 잇는 방법 — 안드로이드 핫스팟 + BLE 보조

### 정한 것

주 경로는 **안드로이드가 Wi-Fi 핫스팟을 열고 아이폰이 붙는 방식**이다.
보조 경로는 **블루투스 저전력(BLE)** 이고 텍스트만 나른다.

### 왜

후보를 전부 따져봤다.

| 후보 | 안드로이드↔아이폰 | 속도 | 판정 |
|---|---|---|---|
| 기내 Wi-Fi | 대부분 단말끼리 통신 차단 | — | 기대할 수 없다 |
| Wi-Fi Direct | 아이폰이 지원 안 함 | — | 불가 |
| Apple Multipeer | 아이폰끼리만 | — | 불가 |
| Google Nearby | 안드로이드 위주 | — | 불가 |
| 블루투스 클래식(SPP) | 아이폰은 애플 인증 부품에만 허용 | — | 불가 |
| **BLE (GATT)** | **양쪽 다 가능** | 초당 수 KB | **채택. 이것뿐이다** |
| ~~핫스팟 + IP 통신~~ | 양쪽 다 가능 | 수십 Mbps | **비행기 모드에서 안 켜진다** |

### 고쳐 적음 — 2026-09-18

**이 표의 마지막 줄이 틀렸었다.** 아래 문단에 "핫스팟은 셀룰러 신호가 없어도
켜진다" 고 적어뒀는데, 실제 기기(갤럭시)에서 해보니 **비행기 모드에서는 핫스팟
메뉴 자체가 잠긴다.**

| 해본 것 | 결과 |
|---|---|
| 비행기 모드 → 핫스팟 | 잠김 |
| 비행기 모드 → Wi-Fi 를 손으로 켜기 → 핫스팟 | **잠김** |
| 핫스팟을 먼저 켜기 → 비행기 모드 | **핫스팟이 꺼진다** |
| 비행기 모드에서 열리는 것 | **블루투스 테더링만** |

블루투스 테더링은 쓸모가 없다. 블루투스 위에 IP 망(PAN)을 까는 것인데 **아이폰은
거기 들어가는 화면이 없다.** iOS 는 애플 기기의 개인용 핫스팟에만 그렇게 붙는다.

셀룰러가 필요 없다는 판단은 맞았지만, **안드로이드가 비행기 모드에서 접속점
만들기를 통째로 잠근다**는 것을 놓쳤다. 문서에서 검증 안 된 추측을 사실처럼
적어둔 탓에 이걸 늦게 알았다.

**따라서 BLE 가 보조가 아니라 유일한 길이다.** 비행 중에는 글·이모지·콕찌르기만
간다. 사진·음성·영상은 못 보낸다.

### 두 폰이 다 안드로이드라면 달라진다

집에 남는 안드로이드가 있어서 둘 다 안드로이드가 되면 **위 표에서 불가로 접은
후보들이 되살아난다.** 특히 Wi-Fi Direct 는 아이폰이 지원 안 한다는 이유 하나로
접은 것이었다.

Wi-Fi Direct 는 테더링이 아니라 **Wi-Fi 기능**이다(`WifiP2pManager`). 비행기
모드에서 잠기는 것은 테더링 쪽이고, Wi-Fi 는 손으로 다시 켤 수 있다. 그래서
**될 가능성이 높지만 확인하지 않았다.** 위에서 한 번 추측을 사실처럼 적어 틀렸으므로
이번에는 확인하기 전까지 여기에 결론을 적지 않는다.

확인하는 법은 앱이 필요 없다. 두 폰 다 비행기 모드 + Wi-Fi 켠 채로

- 설정 → Wi-Fi → ⋮ → Wi-Fi Direct 에서 서로 보이고 연결되는가
- 또는 큰 동영상 하나를 Quick Share 로 보내보고 **빠른가**. 느리면 블루투스로
  떨어진 것이라 Wi-Fi Direct 가 안 된 것이다

되면 그룹 주인이 `192.168.49.1` 에서 DHCP 를 돌리므로, **지금 있는 TCP 코드를
거의 그대로 얹을 수 있다.** 핫스팟을 연 쪽이 게이트웨이인 것과 같은 모양이다.
필요한 것은 그룹을 만드는 Kotlin 모듈뿐이다.

### 포기한 것

- 비행 중 사진·음성·영상. BLE 로는 못 나른다
- 두 아이폰끼리는 연결할 수 없다. 우리 둘에겐 문제가 아니다

## D2. 음성과 영상 — WebRTC를 서버 없이

### 정한 것

`react-native-webrtc`를 쓰되 **STUN·TURN 서버를 하나도 쓰지 않는다.**
연결 협상에 필요한 정보는 우리가 직접 만든 TCP 소켓으로 주고받는다.

### 왜

WebRTC를 쓸 때 보통 필요한 외부 서버는 두 가지다.

- **시그널링 서버**: 두 기기가 서로의 주소를 알려주는 중개자. → 우리는 이미 같은 Wi-Fi 안에 있고 TCP 연결도 있으니, 그 연결로 직접 주고받으면 된다.
- **STUN/TURN 서버**: 공유기 뒤에 숨은 기기의 바깥 주소를 알아내는 도우미. → 같은 Wi-Fi 안이라 서로의 사설 주소로 바로 닿는다. 이런 주소를 host candidate라 하고, 이것만으로 연결이 완성된다.

즉 **인터넷이 필요한 부분을 전부 도려낼 수 있다.** 게다가 같은 결정으로 영상 통화가 거의 공짜로 따라온다. 음성용으로 만든 것을 영상 트랙만 추가하면 되기 때문이다.

음성 코덱은 Opus를 쓴다. 낮은 속도에서도 목소리가 또렷하고 WebRTC에 이미 들어있다.

### 포기한 것

- BLE 보조 경로에선 음성이 안 된다. 대역폭이 턱없이 모자란다.
- 라이브러리가 무겁다. 앱 크기가 늘어난다.

## D3. 앱을 만드는 도구 — React Native + Expo (직접 빌드 방식)

### 정한 것

Expo SDK 56 / React Native 0.85 위에 TypeScript로 만든다.

**57 이 아니라 56 인 이유가 있다.** 57 은 아이폰 빌드에 Xcode 26.4 이상을
요구하고, 그건 macOS Tahoe 26.2 이상을 요구한다. 이 맥은 Sequoia 라
macOS 부터 올려야 한다. 비행 날짜가 정해져 있는데 시스템을 흔들 이유가
없다. 자세한 사정은 [08-build-release.md](./08-build-release.md) 1.1 에 있다.

`expo prebuild`로 네이티브 프로젝트를 만들어 쓴다. **Expo Go 앱으로는 못 돌린다.**

### 왜

- 한 벌만 짜서 두 기기에 올린다. 여행 전에 끝내야 하니 두 벌을 짤 여유가 없다.
- 이미 쓰는 React/TypeScript 지식이 그대로 쓰인다.
- 필요한 네이티브 기능이 전부 라이브러리로 있다: WebRTC, BLE, TCP 소켓, 오디오 세션.
- Expo가 네이티브 설정(권한, 백그라운드 동작, 아이콘)을 설정 파일 하나로 관리해준다. 손으로 Xcode와 Gradle을 만지는 실수를 줄인다.

Expo Go를 못 쓰는 이유는 WebRTC·BLE 같은 네이티브 코드가 들어가기 때문이다. 대신 **개발용 앱(dev client)** 을 한 번 만들어 설치해두고, 그 위에서 코드만 바꿔가며 개발한다.

### 포기한 것

- 첫 빌드 설정에 시간이 든다.
- 네이티브를 건드릴 때마다 다시 빌드해야 한다.

## D4. 메시지 저장 — SQLite

### 정한 것

`expo-sqlite`에 메시지를 저장한다. 설정 같은 작은 값은 `expo-secure-store`와 파일에 나눠 담는다.

### 왜

- 메시지는 시간순으로 쌓이고 계속 늘어난다. 조각조각 읽어오는 일(스크롤)을 잘 하는 건 관계형 저장소다.
- 순서 보장과 중복 방지를 데이터베이스 제약으로 강제할 수 있다. 코드 실수로 같은 메시지가 두 번 들어가는 걸 막는다.
- 내보내기·되돌리기를 만들 때 질의 한 번으로 전체를 꺼낼 수 있다.

### 포기한 것

- 키-값 저장소보다 다루는 코드가 길다. 대신 데이터 접근 코드를 한 층에 가둬서 나머지 코드에 새어나가지 않게 한다.

## D5. 코드 구조 — 클린 아키텍처 + 도메인 주도 설계

### 정한 것

네 겹으로 나눈다: **도메인 → 응용 → 기반 → 화면**.
바깥 겹은 안쪽을 알지만, 안쪽은 바깥을 모른다.

### 왜

이 앱의 핵심 난제는 "연결 방식이 여러 개인데 언제든 바뀐다"는 점이다. 핫스팟이 막히면 BLE로, BLE도 안 되면 웹으로 간다. 이걸 화면 코드에 섞어 넣으면 손을 못 대는 상태가 된다.

그래서 **"메시지를 보낸다"는 뜻은 도메인에 두고, "어떤 길로 보내는가"는 갈아 끼울 수 있는 부품으로 분리**한다. 이러면 연결 방식을 추가해도 화면과 도메인은 그대로다.

덤으로 테스트가 쉬워진다. 도메인과 응용 계층은 진짜 Wi-Fi 없이도 전부 시험할 수 있다.

자세한 구조는 [03-architecture.md](./03-architecture.md)에 있다.

### 포기한 것

- 파일과 인터페이스가 늘어난다. 두 명이 쓰는 앱치고 격식이 있는 편이다. 다만 연결 방식이 세 갈래라 이 격식이 실제로 값을 한다.

## D6. 화면 상태 관리 — Zustand

### 정한 것

화면이 보는 상태는 Zustand에 담는다. 서버가 없으니 데이터 패칭 라이브러리는 쓰지 않는다.

### 왜

- 가볍고 군더더기가 없다.
- 연결 상태처럼 여러 화면이 동시에 보는 값을 다루기 좋다.
- React 바깥(소켓 수신 콜백 등)에서 상태를 바꾸기 편하다. 이 앱은 그런 경우가 많다.

### 포기한 것

- 특별히 없다. 규모에 맞는 선택이다.

## D7. 화면 꾸미기 — 직접 만든 디자인 토큰 + Reanimated

### 정한 것

Tailwind(NativeWind) 대신 **직접 정의한 토큰과 스타일 함수**를 쓴다.
움직임은 `react-native-reanimated`, 그림은 `react-native-svg`로 그린다.

### 왜

- 화면이 열 개 남짓이라 Tailwind를 들일 만큼 규모가 크지 않다. 빌드 설정만 복잡해진다.
- 밝은/어두운 화면 전환을 토큰 한 곳에서 다루면 어긋남이 생기지 않는다.
- 캐릭터가 말할 때 입이 움직이고 연결 상태에 따라 표정이 바뀌어야 한다. 이런 건 SVG를 코드로 그려야 가능하다. 그림 파일로는 못 한다.

### 포기한 것

- 스타일을 쓸 때마다 조금 더 타이핑한다.

## D8. 테스트 — Vitest + React Native Testing Library

### 정한 것

- 도메인과 응용 계층: Vitest로 빠짐없이 시험한다.
- 화면: React Native Testing Library로 주요 흐름을 시험한다.
- 통신 규약: 두 기기를 흉내내는 가짜 연결로 주고받는 전 과정을 시험한다.

Jest 대신 Vitest를 쓰는 이유는 빠르고 설정이 단순해서다. React Native 코드를 직접 다루는 부분만 별도 환경을 둔다.

자세한 전략은 [09-testing.md](./09-testing.md)에 있다.

## D10. 안드로이드 핫스팟을 앱이 직접 켜지 못한다

### 알아둘 것

안드로이드 10부터 **앱이 사용자 몰래 핫스팟을 켤 수 없다.** 시스템 권한이 필요한 동작이라 일반 앱에는 막혀 있다.

이 제약에서 나온 선택:

- 앱은 핫스팟을 **켜주지 못하고**, 대신 **설정 화면으로 데려다준다.** 안내에 "여기를 누르면 핫스팟 설정이 열립니다"를 넣는다.
- 앱은 핫스팟이 켜졌는지 **감지**는 할 수 있다. 자기 IP 주소가 핫스팟 대역(보통 192.168.x.x)에 있는지 확인하는 방식이다.
- 아이폰 쪽도 마찬가지로 Wi-Fi 목록을 앱이 못 연다. 안내로 해결한다.

그래서 F4(처음 쓰는 사람도 쓸 수 있게)가 특히 중요해진다. **연결 과정에서 사람이 해야 할 일이 남아 있기 때문에** 안내 화면의 질이 곧 제품의 질이다.
